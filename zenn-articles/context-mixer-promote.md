## はじめに

個人開発のプロジェクトが20を超えたあたりで、Notionに溜めたドキュメントをAIツールから使うのがしんどくなりました。

少しの追記にもレイテンシがかかり、何度も読み書きしているとトークン消費も馬鹿になりません。ほかのサービスやアプリも検討しましたが、チャットアプリからもCLIのエージェントツールからもアクセスしやすく、AI向きに作られたものが見つかりませんでした。

なので、自分で作りました。**[ContextMixer](https://github.com/iwabuchi404/context-mixer)** という、AIと人間が同じ場所でドキュメントを読み書きするためのナレッジベースです。

この記事では、なぜ作ったのか、どういう設計にしたのか、実際に使ってどうだったかを書きます。

## ContextMixerは何が違うのか

NotionやObsidianは人間が使いやすいことを優先して作られています。それは正しいアプローチだと思いますが、AIからアクセスすることを前提にした設計ではありません。

ContextMixerは**人間とAIの協業**をコンセプトにしています。人間がWeb UIで読み書きしつつ、AIがMCPやREST API経由で同じドキュメントにアクセスできる。どちらの使い勝手も考慮した設計になっています。

### 粒度を選べるドキュメント取得

ContextMixerのAPIは、ドキュメントを「どこまで読むか」を選べるようになっています。

```
GET /docs/:id?view=meta      → タイトル + 概要のみ（数十トークン）
GET /docs/:id?view=outline   → 見出し構造
GET /docs/:id?view=section   → 特定セクションだけ
GET /docs/:id?view=full      → 全文
```

AIが本当にやりたいことは「このドキュメント、自分に関係あるか？」の判断です。それにはタイトルと概要の数十トークンがあれば十分。関係ありそうなら見出し構造を見て、必要なセクションだけ取る。

図書館で目次だけ見て必要な章を開くのと同じことをAPIでやれるようにしました。地味ですが、これでトークン消費が劇的に減ります。

### MCP対応

Claude DesktopやClaude CodeからMCP経由で直接ドキュメントを検索・取得・書き込みできます。OAuth 2.1認証、ツールは9個。

これを入れてから、プロンプトにコンテキストを手動で貼り付ける作業がほぼなくなりました。「このプロジェクトの設計方針を確認して」と言えば、AIが勝手にContextMixerを検索して必要なドキュメントを持ってきてくれます。

### 無料で動く

Cloudflare Workers + D1 + R2の構成で、個人利用の範囲では課金されません。

| サービス | 無料枠 |
|---|---|
| Workers | 10万req/日 |
| D1 | 5GB・500万read/月 |
| R2 | 10GB・転送無料 |

ナレッジベースは一度作ったら何年も使うものなので、ランニングコストがゼロなのは地味に大きいです。

## 技術選定の話

### Cloudflareに全部寄せた理由

スタックはCloudflare Workers + D1 + R2です。全部Cloudflareに寄せたのはシンプルにコストの問題。

ナレッジベースって一度作ったら何年も使うものだし、個人で使うだけなのでできるだけ安く運用できるようにしたかった。使わない月にも金がかかるのは精神的に良くないし、サービス終了のリスクもある。Cloudflareの無料枠は個人利用ならかなりの量使えます。

フレームワークはHonoにしました。Workers上で動くものの中で一番取り回しがいい。D1がSQLiteベースなのでFTS5（全文検索）がそのまま使えて、検索エンジンを別に立てなくていいのも嬉しい。

### VueをやめてHTMXにした

フロントエンドは最初Vue MPAで設計しました。仕事でVue.jsを使っているし、コンポーネントの切り方にも慣れている。

しかし書き始めて気づいた。ContextMixerのUIでやることって、一覧を出す、中身を表示する、テキストエリアで編集する、くらいしかない。状態管理らしい状態管理もない。Vueを入れるとビルドステップが増えるし、Workersへのデプロイも一手間余計にかかる。

HTMXに変えました。サーバーからHTMLフラグメントを返すだけでUIが更新される仕組みで、ビルドステップがなくなる。`public/index.html` と `public/app.js` と `/ui/*` のフラグメントだけ。Honoのルートハンドラがそのままビューを兼ねます。

結果的に、ビルドなし・デプロイは `wrangler deploy` 一発という運用になって、メンテ負荷は確実に下がりました。

### 認証が3種類に分かれた

アクセスしてくる相手が3種類いるので、認証も3つに分かれています。

| 相手 | 認証方式 |
|---|---|
| 人間（ブラウザ） | Clerk セッション認証 |
| AI（REST API） | APIキー（スコープ・コレクション制限あり） |
| AI（MCP） | OAuth 2.1 |

APIキーにはスコープとコレクション制限をつけられるので、「このキーはこのプロジェクトのreadだけ」みたいな運用ができます。信頼度の低い外部サービスに渡すキーの権限を絞れるのは安心感があります。

### FTS5のハイフン罠

全文検索にD1のFTS5を使っていますが、ハイフン入りの語で壊れました。`context-mixer` と検索すると、FTS5はハイフンを「NOT」演算子として解釈してしまう。つまり `context AND NOT mixer` になって、意図しない結果が返ってきます。

修正は `toFtsQuery()` という前処理関数を作って、検索語をフレーズクォートしてからFTSに渡すようにしました。REST・UI・MCPの3箇所で同じ関数を使っています。

**SQLiteのFTS5を使う人は、ハイフン入り語に注意してください。**

## 実際に使ってみて

MCP対応を入れてから本格的にNotionのドキュメントを移して運用を始めました。

自分の個人プロジェクトのナレッジベースとして毎日活用しています。主な利用形態はClaude DesktopとClaude CodeからのMCPアクセス。Web UIは人間が確認用に使うイメージです。

もともと「AIにコンテキストを自動で取ってきてほしい」という体験がほしくて作り始めたので、MCPを入れた時点でようやく当初の目的を達成した感じです。

## 今後の予定

- **Context Bundle** — プロジェクト開発開始時に、spec、decisions、research、rules をまとめて一発で取れる仕組み。`GET /bundles/project-name` で返す想定
- **人間向けUIのリッチ化** — 現在UIは最小限なので、コレクションのエクスポートなど基礎機能を拡充予定
- **OKF対応** — Googleが発表したOpen Knowledge Format（YAMLフロントマター付きMarkdownで知識を表現する標準規格）への対応。内部構造とほぼ同じなので対応は容易なはず
